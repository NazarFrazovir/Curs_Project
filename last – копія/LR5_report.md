### 1.3. Архітектурно-математичне обґрунтування агрегацій

**Чому не можна рахувати середнє для порядкових рейтингів (M2, SonarQube Security Rating A–E).**
Порядкова шкала гарантує лише відношення «гірше/краще»: `A < B < C`. Кодування `A=1, B=2, C=3` умовне. Ми так само могли б закодувати `A=1, B=2, C=10`, і порядок не змінився б. Тоді «середнє» A і C дало б 2 (B) в одному кодуванні та 5,5 (між C і D) в іншому. Результат залежить від довільного кодування, тому методологічно він беззмістовний. Крім того, «A + C = 2B» стверджує, що відстань A→B дорівнює B→C, а шкала цього не визначає. На практиці це означає таке: модуль із рейтингом C (є HIGH-вразливість) «в середньому» з чистим модулем A не стає B. Система містить HIGH-вразливість, і Quality Gate має реагувати на найгірший рівень. Допустимі агрегації для порядкової шкали: **max (worst-case), медіана, мода, частоти по категоріях**.

**Чому для часу відповіді (відносна шкала) використовуємо p95, а не середнє.**
Час відповіді — відносна шкала, тож формально середнє допустиме. Але розподіл латентності сильно скошений вправо, з довгим хвостом. Реальні виміри цього проєкту (сценарій A, ізольовано): **avg = 24,7 мс, медіана = 13,5 мс, p95 = 75,5 мс, max = 196 мс**. Середнє майже вдвічі більше за медіану, бо його тягнуть рідкі повільні запити, і водночас воно втричі менше за p95. Тож середнє не описує ані «типового» користувача (це медіана), ані «найгірших 5 %» (це p95). SLO формулюється як «95 % запитів швидші за 300 мс», і йому відповідає саме p95. Ще дві пастки, які ми закрили в `scripts/loadtest_gate.py`:
* **не можна усереднювати перцентилі** з різних прогонів (середнє p95 ≠ p95 об'єднаної вибірки). Беремо **медіану p95 з N ≥ 3 прогонів**, вона стійка до одного викиду;
* error rate агрегуємо як `Σпомилок / Σзапитів`, а не як середнє відсотків прогонів різної довжини.

**Інтервальна vs відносна шкала (M4 vs MTTR).** Часова мітка `2026-10-08T13:32:30` має умовний нуль (початок календаря чи епохи Unix), тому різниці міток змістовні, а відношення — ні: «13:47 удвічі пізніше за 6:53» не означає нічого. Різниця двох міток (MTTR ≈ 16 хв) вже має абсолютний нуль («відновилися миттєво»), тому це відносна шкала, і для неї коректно сказати «MTTR скоротився вдвічі».

**Номінальна шкала (M5).** Тип коміту `refactor` не «більший» і не «менший» за `feat`, тому медіана чи середнє тут неможливі. Коректно рахувати частки й моду. Baseline M5 одразу дав знахідку: 50 % комітів не типізовані (`Lab2: ...`, `changes`). Без конвенції комітів метрику Q5 неможливо зібрати автоматично, тому для контуру «Команда» правило Conventional Commits є передумовою вимірювань.

## Завдання 2. Стрес-тест на Закон Гудхарта і метрика-балансир

### 2.1. Аналітична декларація ризику

**Обрана метрика:** Line Coverage % модулів стійкості `resilience.py` + `api.py` (контур «Процес», динаміка тестування).

**Краш-сценарій.** Product Owner оголошує KPI: «бонус команді, якщо покриття ≥ 80 %, а за кожен відсоток понад це — додатково». Через спринт дашборд показує зелене покриття, хоча реальна надійність не зросла. Розробники накручують цифру так:

1. **Тести без assert.** Викликати кожну функцію і кожну гілку, нічого не перевіряючи. Рядок вважається покритим, щойно виконався.
2. **Ковтання винятків** (`try: ... except Exception: pass`), щоб «покрити» гілки помилок, навіть якщо код у них падає.
3. **Фейкові залежності без перевірок.** Mock БД повертає будь-що, тест лише проганяє SQL-функцію.
4. **Звуження бази вимірювання:** `omit` у `.coveragerc`, `# pragma: no cover` на складних місцях.

**Демонстрація на коді проєкту.** Я написав «ферму покриття» `experiments/lab5/mutation/test_goodhart_farm.py`: 3 тести, жодного assert. Результат:

| Набір тестів | Тестів | Line Coverage | Mutation Score | Balanced Gate |
|---|---|---|---|---|
| Ферма покриття (Goodhart) | 3 | **98,4 %** | **22,4 %** (33 з 147 мутантів виявлено) | **FAIL** |

Ферма показує покриття навіть **вище**, ніж справжні тести (98,4 % проти 87,5 %), але ламає лише 22 % штучно внесених помилок. Майже всі мутанти, що вижили, — реальні дефекти, які така «тестова база» пропустила б у production:

* `age = int(time.time() + _cache["ts"])` замість `−`: клієнт отримує неправильний вік кешу у відповіді деградації;
* `random.uniform(0, delay / 3)` замість `delay / 2`: зламаний jitter, повтори клієнтів знову синхронізуються (thundering herd);
* `range(2, attempts + 1)` та `if attempt != attempts:`: retry робить на одну спробу менше або взагалі кидає виняток після першої невдачі, і механізм стійкості з ЛР2 фактично вимкнений;
* статус `503` → `504`, `200` → `201`, заголовок `Retry-After` перейменовано або обнулено: клієнт не знає, коли повторити запит.

**Наслідки для кодової бази.** З'являється хибна впевненість: рефакторинг `resilience.py` проходить CI, бо тести нічого не перевіряють. Тестова база росте (і її треба підтримувати), але не захищає. Метрика покриття остаточно втрачає зв'язок із метою Q4/Q2 з GQM.

### 2.2. Специфікація метрики-балансира

| Поле | Значення |
|---|---|
| **Назва** | Mutation Score (частка виявлених мутантів) |
| **Призначення** | Вимірює здатність тестів **помітити помилку**, а не лише виконати рядок. Інструмент вносить у код дрібні дефекти (`−`→`+`, `<`→`<=`, `True`→`False`, зміна констант і рядків) і перевіряє, чи впаде хоча б один тест |
| **Формула** | `MS = (killed + timeout) / (killed + timeout + survived + no_tests) × 100 %` (як у Stryker; `skipped`/`suspicious` не враховуються) |
| **Інструмент** | **mutmut 3.8.1** (безкоштовний, MIT, нативно Python/pytest; Stryker для Python не підтримується повноцінно) |
| **Конфігурація** | `setup.cfg` → `[mutmut] source_paths = resilience.py, api.py`, тести `tests/test_resilience.py`, `tests/test_resilience_contract.py` |
| **Автоматизація** | CI job `quality-metrics`: `mutmut run` → `mutmut export-cicd-stats` → `scripts/balanced_gate.py` |
| **Шкала Стівенса** | Відносна (частка, 0 % = жоден дефект не виявлено) |

**Чому балансир робить накрутку неможливою.** Щоб «вбити» мутанта `now + ts`, тест мусить порівняти `cache_age_s` з очікуваним значенням, тобто перевірити справжній контракт. Тест без assert не вбиває нікого. Тому одночасно підняти Coverage і Mutation Score можна лише одним способом — написати справжні тести, а саме цього й добивається керівництво. Накрутка стає дорожчою за чесну роботу, тож втрачає економічний сенс.

**Що виявив балансир на «чесних» тестах проєкту.** Наявні тести ЛР2 (`tests/test_resilience.py`, 7 тестів, у кожному є assert) **не пройшли** збалансований gate: Coverage 87,5 %, але MS лише 49,7 %. Вижили 56 мутантів, і ще 18 потрапили в `no tests`, бо функція `_query_balance` не виконувалася жодним тестом. За звітом mutmut я написав `tests/test_resilience_contract.py` (14 тестів, які перевіряють точні межі jitter, вік кешу, тіло відповіді 503, журнал спроб, перетворення `Decimal → float` і SQL):

| Етап | Тести | Line Coverage | Mutation Score | killed / survived / no_tests | Gate |
|---|---|---|---|---|---|
| 0. Наявні тести ЛР2 | 7 | 87,5 % | 49,7 % | 73 / 56 / 18 | **FAIL** (MS < 65 %) |
| 1. Ферма покриття (Goodhart) | 3 | 98,4 % | 22,4 % | 33 / 114 / 0 | **FAIL** (MS < 65 %) |
| 2. Наявні + контрактні тести ЛР5 | 21 | 100 % | **95,9 %** | 141 / 6 / 0 | **PASS** |

Аналіз 6 мутантів, що вижили на етапі 2: 4 з них **еквівалентні**, бо змінюють регістр імені HTTP-заголовка (`Warning` → `warning`), а заголовки HTTP регістронезалежні. Ще один теж еквівалентний: `range(1, attempts + 2)` нічого не змінює, бо цикл завершується `raise` на спробі `attempts`. Останній (обрамлення рядка журналу `XX…XX`) — свідомо допустимий. Через еквівалентних мутантів 100 % MS недосяжний і поріг ставимо нижче 100.

### 2.3. Архітектурний щит комплаєнсу (Balanced Quality Gate)

```
PASS  ⇔  (Line Coverage[resilience.py, api.py] ≥ 80 %)  AND  (Mutation Score[resilience.py, api.py] ≥ 65 %)
```

Реалізація: `scripts/balanced_gate.py` (exit 0 = PASS, 1 = FAIL), крок CI `Balanced Quality Gate`.

**Обґрунтування порогів:**
* **80 % coverage** — галузевий орієнтир (SonarQube Sonar way для нового коду). Нижче цього значні частини коду взагалі не виконуються тестами, і мутаційний аналіз для них дає `no_tests`.
* **65 % mutation score** — нижня межа «зрілого» набору тестів. Етап 0 (49,7 %) показав, що поріг відсікає реальні прогалини. Етап 2 (95,9 %) показав, що поріг досяжний із запасом навіть з урахуванням еквівалентних мутантів. Ставити 90 % немає сенсу: це змушувало б писати тести на еквівалентні мутанти (регістр заголовків), що знову веде до «гри з метрикою».
* **Оператор AND**: окремо жодна метрика не стійка. Високий coverage без MS — ферма тестів. Високий MS при низькому coverage — більшість коду поза тестами (MS рахується лише по виконаних мутантах).

**Додаткові заходи проти пункту 4 сценарію:** база вимірювання зафіксована в CI (`--source=resilience,api`, `source_paths` у `setup.cfg`). Зміна цих рядків видна в PR і потребує review, бо `main` захищена.

## Завдання 3. Інфраструктурний краш-тест засобів аналізу

### 3.1. Експеримент 1 — Reliability Test

**Об'єкт:** `reports.py`, найзаплутаніший файл за складністю: `sql_console` CCN 19, `overheads_add` CCN 16, 620 рядків. В оригіналі файл був у **CRLF**, тобто в репозиторії вже були змішані EOL.

|---|---|---|---|---|---|
| Lizard: функцій | 25 | 25 | 25 | 25 | 25 |
| Lizard: NLOC функцій | 452 | 452 | 452 | 452 | 452 |
| Lizard: Σ CCN / max CCN | 115 / 19 | 115 / 19 | 115 / 19 | 115 / 19 | 115 / 19 |
| Lizard: токени | 2749 | 2749 | 2749 | 2749 | 2749 |
| Radon raw: LOC | 620 | 620 | 620 | 620 | **помилка декодування** |
| Radon raw: LLOC / SLOC | 273 / 479 | 273 / 479 | 273 / 479 | **274 / 480** | **помилка** |
| Radon cc: Σ CC | 115 | 115 | 115 | **падіння (U+FEFF)** | **помилка** |
| Radon MI | 30,93 (A) | 30,93 (A) | 30,93 (A) | **падіння** | **помилка** |
| complexipy: Cognitive Σ / max | 78 / 15 | 78 / 15 | 78 / 15 | 78 / 15 | **падіння** |
| Ruff: Code Smells (E,F,W,B,SIM) | 27 | 27 | 27 | 27 | **1** (E902 io-error) |

**Сценарій B — версійність інтерпретатора та інструментів** (файл у CRLF і LF; результати для обох однакові):

| Метрика | Py 3.9.25 | Py 3.11.18 | Py 3.12.13 | Py 3.13.18 | Py 3.11 + **старі** версії інструментів |

| Lizard: Σ CCN / max | 115 / 19 | 115 / 19 | 115 / 19 | 115 / 19 | 115 / 19 |

| Інструмент / версія | Результат |
|---|---|
| complexipy 1.2.0 (з `click<8.2`) | Cognitive Σ = **75**, `sql_console` = 14 |
| complexipy 3.0.0 | Σ = **75**, `sql_console` = 13 |

**Оцінка стійкості інструментів:**
* **EOL (CRLF/LF/змішані) і версія Python 3.9–3.13 на числа не впливають:** усі 4 інструменти стійкі.
* **Кодування — критичний фактор, і помилки тихі.** BOM ламає `radon cc/mi` і зсуває LLOC/SLOC на +1. CP1251 ламає radon і complexipy. Ruff взагалі не повідомляє про збій як про помилку: він видає 1 проблему замість 27, тож дашборд показав би «покращення» в 27 разів. Lizard читає файл «як є» і дає ті самі числа, тобто приховує проблему.
* **Найбільше джерело ненадійності — незафіксовані версії інструментів.** У `requirements-dev.txt` проєкту було `complexipy>=3.0` і `radon>=6.0`. Поріг «Cognitive max ≤ 14» для `sql_console` дав би PASS на 3.0/4.0 і FAIL на 8.3 при незмінному коді — це **хибний FAIL у Quality Gate**. Стара версія complexipy без фіксації транзитивних залежностей просто не запускається.

### 3.2. Експеримент 2 — Stability Test

**Стенд:** Linux, 2 vCPU, 8 GB RAM. Застосунок `python app.py` (як у `Dockerfile`), PostgreSQL 16, у БД 50 товарів і 5000 рухів. k6 на **тій самій машині** — неізольоване середовище. Профіль `ci`: 10 VU, пауза 0,1 с, 80 с. SLO з ЛР2: `p95 < 300 мс AND error rate < 1 %`. Обмеження CPU — квота cgroup CFS на процес застосунку, той самий механізм ядра, що `docker run --cpus`. Шум — 2 паралельні процеси `xz -9e`, що стискають 405 МБ «логів». Кожен сценарій — 3 прогони, порядок по колу (A→B→C→D→E ×3), між прогонами пауза 15 с, перед кожним прогоном перевірка, що не лишилося процесів шуму.

**Метричний профіль стабільності** (медіана з 3 прогонів; у дужках — діапазон p95):

| Сценарій | avg, мс | median, мс | **p95, мс** | p99, мс | RPS | Error rate | RAM (RSS max) | Gate (3 прогони) |
|---|---|---|---|---|---|---|---|---|
| A. Ізольовано | 24,7 | 13,5 | **75,5** (71–83) | 109,3 | 69,4 | 0,00 % | 68 MB | **PASS 3/3** |
| B. + шум `xz` ×2 | 64,8 | 43,2 | **194,4** (188–210) | 270,7 | 51,9 | 0,00 % | 68 MB | PASS 3/3, але використано 65 % бюджету SLO (в ізоляції 25 %) |
| C. `--cpus=0.5` | 33,0 | 16,0 | **108,3** (95–110) | 172,6 | 65,1 | 0,00 % | 68 MB | PASS 3/3 |
| D. `--cpus=0.5` + шум | 71,1 | 47,7 | **207,5** (186–221) | 294,8 | 50,0 | 0,00 % | 68 MB | PASS 3/3, використано 69 % бюджету SLO; p99 одного прогону 324 мс |
| E. `--cpus=0.25` | 178,1 | 155,6 | **473,6** (464–506) | 574,4 | 31,3 | 0,00 % | 68 MB | **FAIL 3/3 — хибне спрацювання** |

```
p95, мс (SLO = 300)          0        100       200       300       400       500
A ізольовано        75,5  |████                            :
B + xz шум         194,4  |██████████                      :
C cpus=0.5         108,3  |█████▌                          :
D cpus=0.5 + xz    207,5  |██████████▌                     :
E cpus=0.25        473,6  |████████████████████████        :   ← FAIL
                                                           SLO
```

**Додаткові спостереження:**
* **Одиночний прогін може обдурити.** Окремий прогін `--cpus=0.5` до серії дав p95 = **430 мс (FAIL)**, а в серії всі 3 прогони тієї ж конфігурації дали 95–110 мс. Причина в тому, що CFS-квота тротлить багатопотоковий процес нерівномірно: потоки Flask на двох ядрах вичерпують 50 мс квоти за 25 мс реального часу й стоять до кінця періоду. Тому gate за **одним** прогоном нестабільний (`experiments/lab5/stability/single_run_cpus05_outlier/`).
* **Індикатор тротлінгу.** Контрольні 30 с: без квоти `nr_throttled` +0, p95 = 64 мс; із квотою 0,25 `nr_throttled` **+268** періодів (≈ 89 % періодів), p95 = 488 мс. Значення `nr_throttled > 0` однозначно показує, що виміряли ліміт інфраструктури, а не код.
* **Шум «краде» CPU і в генератора навантаження.** У сценаріях B/D RPS падає на ≈ 25 % (69 → 52). k6 на тій самій машині теж отримує менше CPU, тож частина затримки виникає в самому генераторі (coordinated omission).
* **RAM застосунку стабільна** (68 MB у всіх сценаріях), отже флуктуації спричинені саме CPU-конкуренцією. Error rate у всіх прогонах 0 %, тобто код працює ідентично.

**Висновок.** Той самий код і та сама БД при зміні лише інфраструктури дають p95 від 71 до 506 мс: розкид ×7. Сценарій E дає стабільний FAIL Quality Gate без жодної зміни в коді. Сценарії B/D використовують 65–69 % бюджету SLO (в ізоляції 25 %), і будь-який додатковий шум (сусідній job на shared-раннері) перетворить їх на FAIL.

### 3.3. Технічна декларація інженерного захисту (впроваджено в гілці `lab5-measurement-governance`)

| # | Ризик з експериментів | Захід | Де в проєкті |
|---|---|---|---|
| 1 | Змішані EOL у репозиторії | Нормалізація всіх файлів до LF; `* text=auto eol=lf` | `.gitattributes`, окремий коміт `chore(lab5): normalize line endings` |
| 2 | BOM / CP1251 тихо ламають метрики | UTF-8 без BOM у редакторі; перевірка до збору метрик (FAIL при BOM, CRLF, не-UTF-8) | `.editorconfig`, `scripts/check_text_hygiene.py`, крок CI `Text hygiene` |
| 3 | Дрейф чисел між версіями інструментів | Жорстка фіксація `==` усіх аналізаторів; оновлення лише окремим PR з перерахунком baseline | `requirements-quality.txt` (замість `complexipy>=3.0`, `radon>=6.0` у `requirements-dev.txt`) |
| 4 | Помилка інструмента = «менше проблем» | Збір із записом версій інструментів у результат; будь-яка помилка парсингу або `E902` → exit 2 (метрики недійсні) | `scripts/collect_metrics.py` |
| 5 | Різний інтерпретатор у різних місцях (`sonar.python.version=3.13`, Dockerfile і CI — 3.11) | Єдиний образ `python:3.11-slim-bookworm` для застосунку, раннера метрик і CI (рекомендовано закріпити digest) | `Dockerfile.quality`, job `quality-metrics` |
| 6 | Ресурси раннера «плавають» | Контейнеризація збору з жорсткими лімітами `--cpus 2 --memory 2g --memory-swap 2g`; фіксований `runs-on: ubuntu-24.04` замість `ubuntu-latest` | `.github/workflows/ci.yml` |
| 7 | CPU-конкуренція застосунку з шумом і генератором | `cpuset` — окреме ядро для `web`, окремі для `k6`; `cpus`/`mem_limit`/`memswap_limit`; tmpfs-БД на кожен прогін; фіксована версія `grafana/k6:0.54.0` | `docker-compose.quality.yml` |
| 8 | Один прогін — випадкова вибірка | Gate за **медіаною p95 з N ≥ 3** прогонів; розкид > 50 % → **INVALID** (перезапуск), а не FAIL | `scripts/loadtest_gate.py` |
| 9 | Тротлінг квоти = хибний FAIL | `nr_throttled > 0` у `cpu.stat` контейнера → **INVALID** | `scripts/loadtest_gate.py --throttled-periods` |
| 10 | Відсутній еталонний профіль навантаження | Профіль `ci` (10 VU, ~70 RPS), що стабільно дає PASS в ізоляції | `load/balance.js` |
| 11 | Goodhart на coverage | Balanced Gate: Coverage ≥ 80 % AND Mutation Score ≥ 65 %; контрактні тести | `scripts/balanced_gate.py`, `setup.cfg`, `tests/test_resilience_contract.py` |

Перевірка `loadtest_gate.py` на зібраних даних:

| Вхід | Результат |
|---|---|
| A, 3 прогони ізольовано | `median p95 = 75.5 мс, spread 16 %` → **PASS** |
| E, 3 прогони `--cpus=0.25` | `median p95 = 473.6 мс` → FAIL; з `--throttled-periods 268` → **INVALID** (правильна класифікація: винна інфраструктура) |
| 2 ізольовані + одиночний викид 430 мс | `spread 476 %` → **INVALID** (а не хибний FAIL) |

Статичний gate на поточному коді (`collect_metrics.py`, ratchet-пороги = baseline): CCN max 24 ≤ 25 AND Cognitive max 28 ≤ 30 → **PASS**. Головна «гаряча точка» — `privacy/sanitizer.py::redact` (CCN 24, Cognitive 28). Після її рефакторингу пороги знижуємо до 15/15.
