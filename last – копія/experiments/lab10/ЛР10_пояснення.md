# ЛР10 — пояснення простими словами

**Тема:** аудит документації, архітектурний паспорт (SDD, ISD, ADR) і передача знань (Handover)

**Суть в одному реченні:** ми перевірили, яким документам про наш проєкт можна вірити, написали нормальну документацію (як система влаштована, як її розгорнути, чому так зроблено), довели, що документація «гниє», якщо змінити код і не оновити її, і підготували пакет, щоб систему могла прийняти інша людина.

Головна теза лекції: **застаріла документація небезпечніша за відсутню**, бо створює ілюзію, що ти розумієш систему.

---

## Загальна термінологія

| Термін | Простими словами |
|---|---|
| **Носій знань** | Будь-яке місце, де записано щось про систему: README, коментарі, конфіги CI, звіти, повідомлення комітів. |
| **Документація продукту** | «Жива»: описує систему **зараз** і має змінюватись разом з нею (README, SDD, ISD). |
| **Документація процесу** | «Історична»: фіксує факт **у минулому** і не оновлюється (звіт ЛР, протокол, повідомлення коміту). |
| **Технічна** | **Що** система робить (функції, API, тести). |
| **Архітектурна** | **Як** вона влаштована (компоненти, зв'язки, дані). |
| **Експлуатаційна** | **Як** її запускати, налаштовувати, розгортати, відновлювати. |
| **Цільові аудиторії** | Розробники (і новачки), QA, DevOps, бізнес. Кожній потрібні різні відповіді. |
| **Documentation as Code** | Документація лежить у git поруч із кодом (Markdown, Mermaid), проходить рев'ю й перевірки як код. |

**Не сплутай (за це −2 бали!):**
- **Продукт vs процес.** README і SDD описують систему **зараз** і мають оновлюватись (продукт). Звіт ЛР5 описує, що ми зробили **тоді**, і його ніхто не оновлює (процес).
- **SDD vs ISD.** SDD — **як система влаштована всередині**: компоненти, модель даних, API. ISD — **де і на чому вона працює**: сервери, контейнери, змінні оточення, CI/CD, бекапи. Коротко: SDD — «будова», ISD — «середовище».

## Завдання 1 — інвентаризація і метрики актуальності

### Термінологія

| Термін | Що це |
|---|---|
| **Інвентаризаційний реєстр** | Таблиця всіх носіїв знань: назва, де лежить, тип, категорія, аудиторія, власник. У нас це `docs/registry.json` (19 записів до ЛР10, 27 після). |
| **Last Updated Age** | Скільки днів тому документ востаннє змінювали: `git log -1 --format=%cs -- файл`. Понад 90 днів — підозрілий, понад 180 — ймовірно застарілий. |
| **Code-Doc Change Ratio** | Скільки разів змінювали код проти того, скільки разів документ. Понад 20 змін коду без оновлення документа — **структурний дрейф**. |
| **Access Evidence** | Чи хтось реально користується документом (посилання на нього, питання). Немає споживача — мертвий документ. |
| **Documentation Decay** | Документ **бреше**: описує систему, якої вже немає. |
| **Dead Documentation** | Документ **нікому не потрібен**: існує, але ним ніхто не користується. |
| **Вердикт** | Що робимо з документом: **оновити**, **видалити** або **deprecated** (позначити застарілим, але залишити). |

### Що ми знайшли
- **README.md** — головна знахідка. Вік **370 днів**, за весь час 1 коміт, а код після нього змінювали **39 разів**. Він «бреше»: пропонує виконати 4 SQL-файли, хоча їх 9, не згадує Docker, просить заповнити `DATABASE_URL`, якого немає в `.env.example`. Це **Decay**.
- **.env.example** — останній рядок злипся (`SECRET_KEY=...GITHUB_TOKEN=`), бракувало половини змінних. **Decay**.
- **setup_db.py** — дублює таблицю з міграції, але з іншими значеннями за замовчуванням. **Decay + Dead**.
- **docker-compose.sonar.yml, scan.sh** — локальний SonarQube з ЛР1, яким ніхто не користується, бо перейшли на SonarCloud. **Dead**.
- **app.py у корені** — файл з одним рядком `import os`. **Dead**, видалено.
- **experiments/lab6/README.md** — демо ЛР6 вже не відтворюється. **Dead**, позначено deprecated.

Усі цифри рахує скрипт **`scripts/doc_audit.py`** через команди git, а не «на око» (за «на око» дають лише 1,5 бала).

### Що показати викладачу
```bash
cd "last – копія"
git log --format="%cs %h %s" -- README.md              # історія README: 2025-11-18 (єдиний коміт до ЛР10) і правки ЛР10
git log --oneline -- inventory.py | wc -l                # скільки разів міняли код
python scripts/doc_audit.py --today 2026-11-23           # уся таблиця метрик + дрейф
```
І відкрий `docs/audit/2026-11-23-baseline.md`: це збережений результат аудиту до виправлень.

## Завдання 2 — архітектурний паспорт

### Термінологія

| Термін | Що це |
|---|---|
| **SDD** (System Design Document) | Як система влаштована: компоненти, хто з ким говорить, модель даних, API. Файл `docs/sdd.md`. |
| **ISD** (Infrastructure Specification Document) | Де і як вона працює: середовища dev/test/prod, контейнери, змінні оточення, CI/CD, бекап. Файл `docs/isd.md`. |
| **ADR** (Architecture Decision Record) | Запис одного архітектурного рішення: контекст, альтернативи, рішення, наслідки. Пишеться в момент рішення і **ніколи не переписується**. |
| **Superseded** | Статус старого ADR, якщо рішення замінили новим. Новий ADR отримує новий номер. |
| **C4-модель** | Діаграми архітектури на 4 рівнях: Context (система і світ), Container (застосунки, БД), Component (модулі всередині), Code. Ми намалювали перші три. |
| **Mermaid** | Діаграми, які пишуться текстом прямо в Markdown. GitHub малює їх сам. |
| **ER-діаграма** | Схема таблиць БД і зв'язків між ними. |
| **API-контракт** | Домовленість: який запит → яка відповідь (код, поля JSON). |
| **RTO** (Recovery Time Objective) | За скільки часу треба відновити систему після аварії. У нас ≤ 1 год. |
| **RPO** (Recovery Point Objective) | Скільки даних можна втратити. У нас ≤ 24 год, бо бекап `pg_dump` робиться раз на добу. |
| **Матриця покриття аудиторій** | Для кожної аудиторії 2–3 питання, на які документація має відповідати, і документ з відповіддю. |

### Що ми зробили
- **`docs/sdd.md`** — C4-діаграми (контекст, контейнери, компоненти), 14 компонентів із посиланнями один на одного і на ISD, ER-діаграма 16 таблиць, усі 79 маршрутів, JSON-контракти.
- **`docs/isd.md`** — 4 профілі розгортання, порядок запуску `db → toxiproxy → web`, 15 змінних оточення по середовищах, CI/CD і ворота якості, реліз і відкат, бекап і відновлення, RTO/RPO.
- **ADR:** 0001 (PostgreSQL і SQL без ORM), 0002 (модульний моноліт на Flask), 0003 → **Superseded** → 0004 (локальний SonarQube замінено SonarCloud). Остання пара показує, як працює статус superseded.
- **`docs/audiences.md`** — 15 питань для 4 аудиторій: 11 прогалин закрито.
- **README переписано:** що робить система, Docker-старт, тести, ролі, API, онбординг.

### Що показати викладачу
Відкрий на GitHub `docs/sdd.md`: Mermaid-діаграми GitHub малює сам. Потім `docs/isd.md` (розділ 6, RTO/RPO), `docs/architecture/adr/README.md` і `docs/audiences.md`.

**Що сказати:** «SDD відповідає, як система влаштована, ISD — де і як вона розгорнута, ADR — чому ми так вирішили. Кожен компонент у SDD має посилання на свій опис розгортання в ISD».

## Завдання 3 — супровід, краш-тест, handover

### Термінологія

| Термін | Що це |
|---|---|
| **Регламент підтримки** | Хто відповідає за документ (**owner**) і як часто його переглядати (**цикл**): експлуатаційні — кожні 90 днів, архітектурні — кожні 180. Файл `docs/maintenance.md`. |
| **«Зміна коду = зміна документації»** | Головне правило: не можна злити зміну коду, не оновивши документи, які вона зачіпає. |
| **Краш-тест Documentation Decay** | Навмисно міняємо код і не чіпаємо документи, щоб довести, що документація стає брехливою. |
| **Structure drift** | Структура в документі (компоненти, маршрути) не збігається з реальною. |
| **Handover Package** | Набір документів, щоб передати систему іншій команді. |
| **Онбординг** | Шлях нової людини від «нічого не знаю» до «запустив систему». |
| **Bus Factor** | Скільки людей має «потрапити під автобус», щоб проєкт зупинився. Bus Factor = 1 означає, що все знає одна людина. |
| **Single point of knowledge** | Частина системи, яку розуміє лише одна людина. |
| **Темна зона** | Важливе знання, яке ніде не записане. |
| **Always Ready to Handover** | Стан, коли систему можна передати будь-якої миті, бо документація завжди актуальна. |

### Що ми зробили
1. **Регламент** (`docs/maintenance.md`): власники, заступники, цикли 90/180 днів, таблиця «змінилось у коді → що оновити», журнал переглядів.
2. **FAIL** (коміт `docs(audit): simulate documentation decay, FAIL`). Додали `alerts.py` з двома новими ендпоінтами (`/api/stock-alerts`, `/api/health`), нову змінну `STOCK_ALERT_THRESHOLD` і змінили порядок запуску в `docker-compose.yml`. Документацію не чіпали.
   - Тести зелені, але `doc_audit --gate` → **FAIL**: 4 документи відстають від коду, 5 розбіжностей.
   - README бреше бізнесу і новачкам, SDD — розробникам і QA, ISD — DevOps.
   - Прогін «на майбутнє» (`--today 2027-03-01`) показує, що вік документів теж перейде поріг 90 днів.
3. **PASS** (коміт `docs(maintenance): restore documentation currency, PASS`). Оновили README, SDD, ISD, `.env.example`, матрицю аудиторій і журнал. Аудит знову **PASS**, 0 розбіжностей.
4. **Handover** (`docs/handover.md`):
   - реєстр документів зі статусом;
   - онбординг у 5 кроків;
   - **Bus Factor = 1**: два імені в git (`nazar` і `NazarFrazovir`), але це одна людина;
   - 3 темні зони: паролі в БД відкритим текстом, подвоєний префікс маршрутів, кілька git-ідентичностей;
   - план: заступники, обов'язкове рев'ю, CI-job `docs-currency`.

   Вердикт: документаційно система готова до передачі, організаційно — ні, поки Bus Factor = 1.
5. Додали в CI job **`docs-currency`**: тепер GitHub сам перевіряє актуальність документації на кожен push.

### Що показати викладачу
```bash
git log --oneline -6                                   # коміти FAIL і PASS
git show f0d7a88 --stat                                # що змінили в краш-тесті
git show lab10-documentation:"last – копія/scripts/doc_audit.py" > /tmp/doc_audit.py   # актуальна версія аудитора
git checkout f0d7a88                                   # стан FAIL
cd "last – копія" && python /tmp/doc_audit.py --gate; echo "exit=$?"      # FAIL, exit=1
cd .. && git checkout lab10-documentation              # стан PASS
cd "last – копія" && python scripts/doc_audit.py --gate; echo "exit=$?"   # PASS, exit=0
```
Потім відкрий `docs/handover.md`: розділ Bus Factor і вердикт.

**Що сказати:** «Я додав два ендпоінти і змінив порядок запуску, не оновивши документи. Тести пройшли, але README, SDD і ISD почали брехати: це видно в аудиті. Після оновлення аудит знову зелений, а CI тепер сам не пропустить таку зміну».
