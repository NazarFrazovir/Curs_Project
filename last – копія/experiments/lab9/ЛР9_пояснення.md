# ЛР9 — пояснення простими словами

**Тема:** SQALE, фінансова оцінка технічного боргу і вимірювання розміру системи (FPA & UCP)

**Суть в одному реченні:** ми переводимо «поганий код» у гроші (скільки коштує його виправити і скільки ми втрачаємо, поки не виправили) і міряємо, «скільки функціональності» в модулі, щоб потім рахувати бюджет нових задач ще до написання коду.

На відміну від минулих лаб, тут аналізуємо **чужий великий open-source проєкт** — **InvenTree** (система складського обліку, 171 тис. рядків). У нашому репозиторії лежать лише скрипт, дані та розрахунки.

---

## Загальна термінологія

| Термін | Простими словами |
|---|---|
| **Технічний борг** | «Недоробки» в коді (дублювання, складні функції, порушення правил), які колись доведеться виправляти. Як кредит: не віддаєш — платиш відсотки. |
| **SQALE** | Стандарт, за яким SonarQube оцінює технічний борг у хвилинах роботи на виправлення. |
| **ncloc** | Non-Comment Lines Of Code — рядки коду без коментарів і порожніх рядків. |
| **Forensic-аудит** | Незалежна перевірка «як слідчий»: беремо сирі дані й самі перераховуємо, чи правду каже інструмент. |
| **REST API** | Отримання даних HTTP-запитом (`curl`) замість кліків на сайті. |
| **Software Economics** | Розділ інженерії, де якість коду переводять у гроші. |

## Завдання 1 — SQALE-аудит великого проєкту

### Термінологія

| Термін | Що це |
|---|---|
| **sqale_index** | Загальний технічний борг у **хвилинах** роботи на виправлення (Remediation Cost). |
| **sqale_rating** | Літерна оцінка супроводжуваності A…E. API віддає числом: 1.0 = A, 5.0 = E. |
| **Remediation Cost** | Вартість (у часі) виправлення всіх проблем. |
| **Людино-година / людино-день** | 1 година / 8 годин роботи одного інженера. |
| **TDD (Technical Debt Density)** | Щільність боргу: яку частку від вартості написання системи з нуля становить борг. |
| **Development cost** | Скільки часу пішло б на написання системи з нуля. SQALE рахує 30 хв на рядок. |
| **Project key / organization key** | Унікальні ідентифікатори проєкту й організації в SonarQube Cloud (видно в URL). |

### Що ми зробили
1. Через API знайшли Python-проєкти з > 50 000 рядків і обрали **InvenTree** (key `inventree_InvenTree`). Він з того ж домену, що й наш склад.
2. Запит `api/measures/component` дав: **ncloc = 171 018, sqale_index = 5 026 хв, sqale_rating = 1.0 (A)**. Сира відповідь збережена в `experiments/lab9/report.json`.
3. Порахували:
   - 5026 / 60 = **83,77 люд.-год**; / 8 = **10,47 люд.-днів**;
   - час написання з нуля = 171 018 × 30 / 60 = 85 509 год;
   - **TDD = 83,77 / 85 509 = 0,098 %**.
4. Перевірка: 0,098 % ≤ 5 % → рейтинг **A**, хмара теж каже **A**, отже збігається. Додатково збіглися `development_cost` і `sqale_debt_ratio` (0,1 %) із хмари.

### Що сказати викладачу
«Обрав InvenTree, 171 тис. рядків. Дані вивантажив через API, ось запит і сирий JSON. Борг 10,5 людино-днів, TDD 0,098 %, це рейтинг A, збігається з Sonar».

**Як повторити запит самому:**
```bash
curl -s "https://sonarcloud.io/api/measures/component?component=inventree_InvenTree&metricKeys=sqale_index,ncloc,sqale_rating"
```
(Проєкт аналізується щодня, тому цифри можуть трохи відрізнятися від тих, що в звіті. Це нормально.)

## Завдання 2 — фінансовий симулятор

### Термінологія

| Термін | Простими словами |
|---|---|
| **HOURLY_RATE** | Ставка розробника, $/год (у нас 40). |
| **OVERLOAD_COEFF** | Накладні витрати компанії (податки, офіс, менеджмент): ×1,3. Година розробника коштує компанії $40 × 1,3 = $52. |
| **Principal (тіло боргу)** | Скільки коштує виправити весь борг **зараз**: години боргу × $52. Це разова **інвестиція**. |
| **Cost of Delay (CoD, вартість затримки)** | Скільки компанія **втрачає щомісяця**, поки борг не виправлено. За правилом лаби: 1 год на кожні 100 рядків на боротьбу з регресійними багами. |
| **Регресійний баг** | Коли щось, що раніше працювало, ламається після зміни. |
| **Дисконтування** | «Гроші завтра дешевші, ніж сьогодні». $100 через місяць при ставці 1 % коштують сьогодні $100 / 1,01 = $99,01. |
| **DISCOUNT_RATE** | Ставка знецінення грошей, 1 % на місяць. |
| **NPV (Net Present Value, чиста приведена вартість)** | Сума всіх майбутніх вигод, перерахованих на «сьогоднішні» гроші, мінус інвестиція. NPV > 0 означає, що інвестиція вигідна. |
| **Кумулятивна NPV** | NPV, накопичена до місяця t включно. |
| **Payback Period (точка окупності)** | Перший місяць, коли NPV стала > 0, тобто інвестиція повернулась. |
| **Quality Gate** | Ворота якості: PASS, якщо окупилось за 6 місяців, інакше FAIL. |
| **Змінні оточення (Environment Variables)** | Налаштування, які передаються програмі ззовні (`HOURLY_RATE=40 python ...`), а не пишуться в коді. |

### Формули
```
Principal = sqale_index / 60 × rate × overload            = 83,77 × 52  = $4 355,87
CoD       = ncloc / 100 × 1 год × rate × overload          = 1 710,18 × 52 = $88 929,36 / міс
NPV_t     = Σ (CoD / 1,01^k) для k = 1..t  −  Principal
```

### Що ми зробили
- **`scripts/software_economics.py`** читає `report.json` і змінні оточення. Нічого не захардкоджено: числа беруться з JSON.
- У циклі `for t in 1..6` рахує коефіцієнт дисконтування, приведену вартість і кумулятивну NPV. Умова `if NPV_t > 0` визначає місяць окупності.
- Генерує **`FINANCIAL_LEDGER.md`** з таблицею і статусом. Результат: **окупність на 1-му місяці, PASS**.
- **`tests/test_software_economics.py`** — 11 тестів, зокрема сценарій **FAIL** (коли борг завеликий) і окупність на 4-му місяці.

### Головний висновок
Principal залежить від боргу, CoD — від розміру системи. Окупність за 6 місяців буває тоді, коли **TDD < 11,6 %**. Отже, проєкти з рейтингом A/B завжди PASS, а D/E — FAIL. Чим більша система, тим швидше окупається рефакторинг. Мінус моделі: CoD не залежить від реального боргу, тому для «чистого» проєкту він завищений.

### Що показати викладачу
```bash
cd "last – копія"
HOURLY_RATE=40 OVERLOAD_COEFF=1.3 DISCOUNT_RATE=0.01 python scripts/software_economics.py experiments/lab9/report.json
cat FINANCIAL_LEDGER.md
pytest -q tests/test_software_economics.py
```
**Зроби скріншот терміналу після першої команди: він потрібен у звіт.**

**Якщо спитають «що таке Cost of Delay?»** (за це −2 бали, якщо не відповісти): «Це гроші, які бізнес втрачає щомісяця через те, що борг не виправлено: інженери витрачають час на регресійні баги замість нових функцій. Після рефакторингу ці втрати зникають, тому CoD — це щомісячний прибуток від інвестиції в рефакторинг».

## Завдання 3 — FPA і UCP

### Термінологія FPA (Function Point Analysis, IFPUG)

| Термін | Що це | Приклад у нас |
|---|---|---|
| **Функціональна точка (FP)** | Одиниця «корисної функціональності» з погляду користувача, незалежна від мови програмування. | — |
| **ILF** (Internal Logical File) | Внутрішній логічний файл: дані, які модуль **сам змінює**. | Company, ManufacturerPart, SupplierPart |
| **EIF** (External Interface File) | Зовнішні дані, які модуль лише **читає**. | Part, StockItem, замовлення, курси валют |
| **EI** (External Input) | Вхідна транзакція: створити / змінити / видалити. | POST/PUT/DELETE |
| **EO** (External Output) | Вихід з **обчисленнями**: звіт, статистика, експорт. | список компаній з кількістю деталей, експорт CSV |
| **EQ** (External Query) | Простий запит: прочитати і показати **без обчислень**. | GET деталі виробника |
| **DET** (Data Element Type) | Кількість полів, з якими працює елемент. | 18 полів у Company |
| **RET** (Record Element Type) | Підгрупа записів усередині ILF. | SupplierPart + PriceBreak = 2 RET |
| **FTR** (File Type Referenced) | Скільки файлів (ILF/EIF) зачіпає транзакція. | створення SupplierPart зачіпає 4 |
| **Складність L / A / H** | Low / Average / High. Визначається за таблицями з RET/FTR і DET. | — |
| **UFP / VAF** | Ненормалізований розмір / коефіцієнт поправки (ми взяли 1,0). | — |

**Ваги:** ILF 7/10/15, EIF 5/7/10, EI 3/4/6, EO 4/5/7, EQ 3/4/6.

### Термінологія UCP (Use Case Points, Карнер)

| Термін | Що це |
|---|---|
| **Use Case (прецедент)** | Сценарій «хто що робить із системою». |
| **Актор** | Той, хто взаємодіє з системою: людина або інша програма. |
| **UAW** | Сума ваг акторів: простий (API/CLI) = 1, середній (HTTP) = 2, складний (людина через GUI) = 3. |
| **UUCW** | Сума ваг use cases: ≤ 3 кроки = 5, 4–7 = 10, > 7 = 15. |
| **UUCP** | UAW + UUCW. |
| **TCF / ECF** | Технічні / середовищні коефіцієнти (ми взяли 1,0). |
| **UCP** | UUCP × TCF × ECF. |
| **UML Use Case діаграма** | Малюнок: актори (чоловічки) з'єднані з овалами-прецедентами всередині рамки системи. |

### Калібрування

| Термін | Що це |
|---|---|
| **Реверс-інжиніринг** | Відновлення вимог з готового коду: дивимось моделі, API, методи і розуміємо, що система вміє. |
| **Git-години** | Оцінка витраченого часу з історії комітів. Коміти одного автора з паузою < 2 год — одна сесія. |
| **PF (Productivity Factor)** | Скільки годин команда витрачає на 1 UCP: PF = години / UCP. |
| **Change Request (CR)** | Запит замовника на зміну чи нову функцію. |

### Що ми зробили
1. Обрали модуль **`company`** InvenTree (каталог постачальників): 4 класи `Company → ManufacturerPart → SupplierPart → SupplierPriceBreak`.
2. **Реверс-інжиніринг:** виписали поля моделей, 8 API-маршрутів і сигнатури методів (`clean`, `save`, `get_price`, `on_order`…).
3. **FPA:** 3 ILF + 4 EIF + 14 EI + 8 EO + 4 EQ = **167 FP**.
4. **UCP:** 3 актори (UAW = 6) + 10 use cases (UUCW = 90) = **96 UCP**.
5. **Git:** 344 коміти, 14 авторів, 588 git-годин. Частка наших 4 класів 84,9 %, тобто **499,5 люд.-год**.
6. **PF = 499,5 / 96 = 5,2 год/UCP** (еталон Карнера — 20). Git-години занижені, бо не враховують обговорення і рев'ю, тому реальний діапазон 5,2–20.
7. **Оцінка CR:** новий use case із 6 кроків = 10 UCP × 5,2 = 52 год × $52 = **$2 705**.

Файли: `experiments/lab9/fpa_ucp_calculator.xlsx` (усі таблиці з формулами), `use_case.drawio` (відкривається в draw.io) і `use_case.png`.

### Різниця FPA і UCP (за плутанину −2 бали!)
- **FPA** міряє **дані й операції над ними**: таблиці, введення, виведення, запити. Не залежить від мови і від ООП.
- **UCP** міряє **поведінку**: хто користується системою і скільки кроків у сценаріях. Зручно на ранньому етапі, коли є лише use case діаграма.

Одна й та сама система дає різні числа (167 FP і 96 UCP), бо це різні «лінійки».

### Що сказати викладачу
«Взяв модуль постачальників InvenTree. З моделей і API отримав 167 функціональних точок, з use case діаграми 96 UCP. З git-історії команда витратила ~500 годин, отже PF = 5,2 год на UCP. Тепер новий CR можна оцінити до написання коду: рахуємо кроки сценарію, переводимо в UCP і множимо на PF і ставку».
